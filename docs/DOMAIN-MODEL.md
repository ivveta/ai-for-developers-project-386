# Доменная модель «Календарь звонков»

Документ даёт общее бизнес-описание домена и фиксирует модельные решения, которых нет в
[`SPECIFICATION.md`](./SPECIFICATION.md). Поля сущностей, инварианты (И1–И8), правила генерации
слотов, порядок проверок, пользовательские сценарии и HTTP API описаны в спецификации и здесь
не повторяются. Ссылки вида Рn и § ведут на спецификацию.

## 1. Обзор

«Календарь звонков» — упрощённый сервис бронирования времени на созвоны. Владелец календаря
публикует виды брони (типы событий), любой посетитель выбирает свободный слот и записывается
на встречу, владелец видит единый список предстоящих встреч. Авторизации, личных кабинетов
и интеграций с внешними календарями нет.

Домен состоит из четырёх понятий и одной роли-участника:

| Понятие | Англ. | Хранение | Назначение |
|---|---|---|---|
| Владелец календаря | Owner, Host | Не хранится (заранее заданный профиль) | Публикует типы событий, просматривает предстоящие встречи |
| Тип события | EventType | Хранится | Шаблон встречи: название, описание, длительность; задаёт сетку слотов |
| Слот | Slot | Не хранится (вычисляется на лету) | Интервал времени, доступный или занятый для брони |
| Бронирование | Booking | Хранится | Подтверждённая запись гостя на конкретный интервал |
| Гость | Guest | Не хранится (анонимный посетитель) | Выбирает слот и оформляет бронирование |

Связи между понятиями:

- Владелец один (Р11), ему принадлежат все типы событий и все бронирования — связь «один
  ко многим» неявная, без ссылок в данных.
- Один тип события имеет много бронирований: `EventType` 1—∞ `Booking` (по полю
  `Booking.eventTypeId`).
- Слот не связан с хранилищем напрямую: он вычисляется из длительности типа события
  и множества уже существующих бронирований.

Хранятся только две сущности — `EventType` и `Booking`. Владелец и слот сущностями хранилища
не являются, и вводить для них таблицы не нужно.

## 2. Владелец — роль, а не запись

Владелец — единственный заранее заданный профиль (Р11). Поскольку аутентификации нет (Р10),
а поддержка нескольких владельцев исключена из объёма (§1.2), в доменной модели владелец —
это **роль и набор констант отображения** (имя `Tota`, подпись `Host`, §10), а не запись
в базе данных.

## 3. Жизненный цикл сущностей

- Тип события после создания не изменяется и не удаляется (§3) — сущность фактически
  иммутабельна.
- Бронирование после создания не изменяется и не отменяется (Р9). Единственная «эволюция» —
  переход из будущих в прошедшие по мере течения времени: в админский список
  `/admin/bookings` попадают только встречи, которые ещё не начались (§7.9).
