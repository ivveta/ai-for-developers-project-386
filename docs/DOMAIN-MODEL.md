# Доменная модель «Календарь звонков»

Документ описывает доменные сущности системы и публичный сценарий гостя. Изложение опирается на
[`SPECIFICATION.md`](./SPECIFICATION.md): номера решений (Р1–Р11), инвариантов (И1–И8), сценариев
(С1–С5) и разделов (§) ведут на него.

## 1. Обзор

Система оперирует четырьмя понятиями и одной ролью-участником:

| Понятие | Англ. | Хранение | Назначение |
|---|---|---|---|
| Владелец календаря | Owner, Host | Не хранится (заранее заданный профиль) | Публикует типы событий, просматривает предстоящие встречи |
| Тип события | EventType | Хранится | Шаблон встречи: название, описание, длительность; задаёт сетку слотов |
| Слот | Slot | Не хранится (вычисляется на лету) | Интервал времени, доступный или занятый для брони |
| Бронирование | Booking | Хранится | Подтверждённая запись гостя на конкретный интервал |
| Гость | Guest | Не хранится (анонимный посетитель) | Выбирает слот и оформляет бронирование |

Связи между понятиями:

- Владелец один (Р11), ему принадлежат все типы событий и все бронирования — связь «один ко многим»
  неявная, без ссылок в данных.
- Один тип события имеет много бронирований: `EventType` 1—∞ `Booking` (по полю `Booking.eventTypeId`).
- Слот не связан с хранилищем напрямую: он вычисляется из длительности типа события и множества
  уже существующих бронирований.

Хранятся только две сущности — `EventType` и `Booking`. Владелец и слот сущностями хранилища не
являются, и вводить для них таблицы не нужно.

## 2. Владелец (Owner / Host)

Владелец — единственный заранее заданный профиль, которому принадлежит весь календарь (Р11).
Аутентификации в системе нет (Р10): владелец не входит в систему, а просто работает в админской
части по прямым маршрутам (`/admin/...`). Поддержка нескольких владельцев сознательно исключена
из объёма (§1.2).

Поэтому владелец — это **роль и набор констант отображения**, а не запись в базе данных:

| Поле | Значение | Источник |
|---|---|---|
| Имя | `Tota` | Начальные данные, §10 |
| Подпись роли | `Host` | Начальные данные, §10 |

Права владельца (§3): создавать типы событий и просматривать единый список предстоящих встреч
с контактами гостей. Владельцу недоступны отмена и изменение бронирований, а также изменение
и удаление типов событий — этих операций нет ни у одной роли (Р9).

Поскольку технических барьеров между ролями нет, разделение «гость / владелец» существует только
на уровне маршрутов и пользовательских путей — это осознанное ограничение учебного проекта (§3).

## 3. Тип события (EventType)

Тип события — хранимый шаблон встречи. Определяет, на какие встречи может записаться гость, и задаёт
шаг сетки слотов: длительность типа равна шагу сетки (Р2).

| Поле | Тип | Обяз. | Ограничения | Описание |
|---|---|:---:|---|---|
| `id` | string | да | `^[a-z0-9-]{1,64}$`, уникален | Идентификатор-slug, задаёт владелец. Используется в URL |
| `title` | string | да | 1–100 символов | Название встречи |
| `description` | string | да | 1–500 символов | Описание для карточки в каталоге |
| `durationMinutes` | int | да | Только `15` или `30` | Длительность встречи, она же — шаг сетки слотов |
| `createdAt` | instant | да | Задаётся системой | Момент создания, UTC |

Инварианты сущности:

| № | Правило |
|---|---|
| И1 | `EventType.id` уникален в пределах системы. Нарушение при создании — `409 event_type_id_taken` |
| И2 | `durationMinutes ∈ {15, 30}`. Нарушение при создании — `400 validation_error` |

Дополнительные свойства:

- Тип события после создания не изменяется и не удаляется (§3) — сущность фактически иммутабельна.
- Сортировка в каталоге и в админском списке — по `createdAt` по возрастанию (§7.4, §8.2).
- На старте системы создаются два типа: `meeting-15` и `meeting-30` (§10).

## 4. Слот (Slot)

Слот — **вычисляемая структура**, в хранилище отсутствует (§4.4). Существует только в ответах API
и в интерфейсе выбора времени.

| Поле | Тип | Описание |
|---|---|---|
| `start` | instant | Начало слота |
| `end` | instant | Конец слота, `start + durationMinutes` типа события |
| `status` | enum | `free` — свободен, доступен для брони; `busy` — пересекается с существующим бронированием |

### 4.1. Генерация сетки (§5.1)

Слоты дня строятся от начала рабочего дня с шагом, равным длительности типа события `D`:

```text
start(k) = 09:00 + k × D минут
end(k)   = start(k) + D
k = 0 … (540 / D − 1)
```

Рабочий день — 09:00–18:00 по `Europe/Moscow` (540 минут), все 7 дней недели (Р3, Р4):

| Длительность | Слотов в дне | Первый слот | Последний слот |
|---:|---:|---|---|
| 15 мин | 36 | 09:00–09:15 | 17:45–18:00 |
| 30 мин | 18 | 09:00–09:30 | 17:30–18:00 |

30 кратно 15, поэтому сетки двух типов согласованы: границы 30-минутных слотов всегда совпадают
с границами 15-минутных.

### 4.2. Отбор слотов в выдачу

Из построенного набора исключаются (для них статуса нет — они не показываются вовсе):

- слоты, начало которых раньше текущего момента (Р8);
- слоты за пределами окна записи — 14 календарных дней, считая сегодняшний первым; верхняя
  граница — 18:00 четырнадцатого дня (Р6, §5.2).

Запрос слотов на дату вне окна — не ошибка, а пустой список (§5.5).

### 4.3. Занятость (§5.3)

Слот занят, если пересекается **хотя бы с одним** бронированием — любого типа события (Р7).
Интервалы полуоткрытые: `[start, end)`; смежные интервалы не пересекаются.

```text
пересекаются(a, b) = a.start < b.end AND b.start < a.end
```

Проверки совпадения времени начала недостаточно. Ключевые случаи:

| Существующая бронь | Смотрим слоты типа | Результат |
|---|---|---|
| 30 мин, 09:00–09:30 | 15 мин | Заняты 09:00–09:15 и 09:15–09:30; 09:30–09:45 свободен |
| 15 мин, 09:15–09:30 | 30 мин | Занят 09:00–09:30 (начала не совпадают); 09:30–10:00 свободен |
| 15 мин, 09:00–09:15 | 30 мин | Занят 09:00–09:30 |
| 30 мин, 09:30–10:00 | 15 мин | Заняты 09:30–09:45 и 09:45–10:00 |

## 5. Бронирование (Booking)

Бронирование — хранимая подтверждённая запись гостя на конкретный интервал по конкретному типу
события.

| Поле | Тип | Обяз. | Ограничения | Описание |
|---|---|:---:|---|---|
| `id` | uuid | да | Генерируется системой | Идентификатор брони |
| `eventTypeId` | string | да | Существующий `EventType.id` | Ссылка на тип события |
| `startAt` | instant | да | См. инварианты И4, И6, И7 | Начало встречи, UTC |
| `endAt` | instant | да | Вычисляется системой | Конец встречи, UTC. Клиентом не передаётся |
| `guestName` | string | да | 1–100 символов | Имя гостя |
| `guestEmail` | string | да | Валидный email, до 254 символов | Email гостя |
| `notes` | string | нет | До 1000 символов | Заметка гостя |
| `createdAt` | instant | да | Задаётся системой | Момент создания, UTC |

Инварианты сущности:

| № | Правило |
|---|---|
| И3 | `endAt = startAt + durationMinutes` типа события на момент создания брони |
| И4 | `startAt < endAt` |
| И5 | Никакие две брони не пересекаются. Инвариант глобальный, не зависит от `eventTypeId` |
| И6 | `startAt` выровнено по сетке типа события: `начало_рабочего_дня + k × durationMinutes` |
| И7 | Бронь целиком в рабочем дне: `09:00 ≤ startAt`, `endAt ≤ 18:00` по `Europe/Moscow` |
| И8 | `eventTypeId` ссылается на существующий `EventType` |

### 5.1. Создание брони: порядок проверок (§9.3)

Проверки выполняются последовательно; первая сработавшая определяет ответ:

| Шаг | Проверка | Ответ при нарушении |
|---:|---|---|
| 1 | Формат и обязательность полей | `400 validation_error` |
| 2 | Существование типа события | `404 not_found` |
| 3 | Выравнивание по сетке и рамки рабочего дня (И6, И7) | `400 validation_error` |
| 4 | Не в прошлом и в пределах 14-дневного окна | `422 out_of_window` |
| 5 | Пересечение с существующими бронями (И5) | `409 slot_taken` |

### 5.2. Конкурентность (§5.4)

Проверка свободности интервала и вставка брони выполняются атомарно: при одновременных запросах
ровно один получает `201`, остальные — `409 slot_taken`. Промежуточное состояние с двумя
пересекающимися бронями недопустимо; И5 обеспечивается на уровне хранилища (ограничение
непересечения интервалов либо проверка в сериализуемой транзакции), а не только прикладным кодом.

### 5.3. Жизненный цикл

Бронирование после создания не изменяется и не отменяется (Р9). Единственная «эволюция» — переход
из будущих в прошедшие по мере течения времени: в админский список `/admin/bookings` попадают
только встречи, которые ещё не начались (§7.9).

## 6. Публичный сценарий гостя

Гость — анонимный посетитель без учётной записи. Его сквозной путь (сценарии С1–С3, маршруты §7.1):

`/` → `/book` → `/book/{eventTypeId}` → `/book/{eventTypeId}/success`

### 6.1. Шаги сценария

| Шаг | Маршрут | Действие гостя | Ответ системы | API |
|---:|---|---|---|---|
| 1 | `/` | Нажимает «Записаться» | Переход в каталог | — |
| 2 | `/book` | Просматривает карточку владельца (`Tota`, `Host`) и список типов: название, описание, бейдж длительности | Показаны все типы событий, по `createdAt` ↑ | `GET /api/event-types` |
| 3 | `/book/{eventTypeId}` | Открывает карточку типа; видит календарь текущего месяца: даты в окне записи кликабельны и со счётчиком «N св.», остальные неактивны | Календарь и карточка типа | `GET /api/event-types/{id}`, `GET .../slots?date=` |
| 4 | там же | Выбирает дату | Панель слотов дня: интервалы «HH:MM - HH:MM» со статусами «Свободно» / «Занято» | `GET .../slots?date=` |
| 5 | там же | Выбирает свободный слот, нажимает «Продолжить» | Показ формы записи; слот фиксируется в query-параметре `startAt`. Пока слот не выбран, кнопка неактивна | — |
| 6 | там же (`?startAt=...`) | Проверяет сводку (тип, дата, время, длительность), заполняет имя, email, при желании заметку; подтверждает | Валидация и создание брони | `POST /api/bookings` |
| 7 | `/book/{eventTypeId}/success` | Видит экран успеха с деталями встречи | Бронь создана; ссылка в каталог для новой записи | — |

### 6.2. Альтернативные ветки

| Ситуация | Поведение системы |
|---|---|
| В системе нет типов событий | Каталог показывает пустое состояние «Пока нет типов событий» |
| Несуществующий `eventTypeId` в URL | «Тип события не найден» и ссылка в каталог (`404 not_found`) |
| В выбранный день нет свободных слотов | Пустое состояние панели «На этот день свободных слотов нет» |
| Данные формы не прошли валидацию | Ошибки у полей, введённые данные сохранены, бронь не создана (`400 validation_error`) |
| Время вне окна записи или в прошлом | `422 out_of_window`, бронь не создана |
| Слот заняли, пока гость заполнял форму | `409 slot_taken`: сообщение «Этот слот только что заняли. Выберите другое время» и возврат к выбору слота с обновлёнными данными |

### 6.3. Результат сценария

Созданное бронирование занимает интервал глобально: пересекающиеся слоты всех типов событий
становятся `busy` для всех последующих гостей (И5). Отмены и изменения записи у гостя нет (Р9);
контакты гостя видны только владельцу в админском списке (§3).

## 7. Сводка инвариантов

| № | Сущность | Правило |
|---|---|---|
| И1 | EventType | `id` уникален в пределах системы |
| И2 | EventType | `durationMinutes ∈ {15, 30}` |
| И3 | Booking | `endAt = startAt + durationMinutes` типа события на момент создания |
| И4 | Booking | `startAt < endAt` |
| И5 | Booking | Никакие две брони не пересекаются; инвариант глобальный, обеспечивается хранилищем |
| И6 | Booking | `startAt` выровнено по сетке слотов типа события |
| И7 | Booking | Бронь целиком внутри рабочего дня 09:00–18:00 по `Europe/Moscow` |
| И8 | Booking | `eventTypeId` ссылается на существующий `EventType` |

## 8. Хранение и время (§4.6)

- Метки времени хранятся в UTC; преобразование в `Europe/Moscow` — на границе системы
  (API-ответы, интерфейс).
- Уникальный индекс по `EventType.id`.
- Индекс по `Booking.startAt` — для выборки слотов дня и списка предстоящих встреч.
