# План: подготовка артефактов контракта + фронтенд против мок-сервера Prism

Составлен на основании [`SPECIFICATION.md`](./SPECIFICATION.md) (§7–§9, §11),
[`STRUCTURE-PLAN.md`](./STRUCTURE-PLAN.md) и [`TYPESPEC-PLAN.md`](./TYPESPEC-PLAN.md).

## Контекст и решение о порядке

Контракт в `api/` описан полностью и сверен со спецификацией, но пакет не собран: зависимости не
установлены, `openapi.yaml` и `types/schema.d.ts` не сгенерированы, каркас монорепо отсутствует,
бэкенда нет.

**Принятое решение:** фронтенд делаем до бэкенда, против мок-сервера Prism, поднятого из
`api/openapi/openapi.yaml` (рекомендация ТЗ: «для работы с API по контракту во время разработки —
Prism»). Контракт зафиксирован в TypeSpec, поэтому переход на реальный API не потребует
переписывания фронта — меняется только base URL в `VITE_API_URL`. Это отклонение от порядка в
STRUCTURE-PLAN («Порядок реализации», шаги 3–4) — документ обновляется на шаге 0.

Требования ТЗ по изоляции фронта, фиксируем здесь:
- фронтенд — отдельная часть приложения (пакет `frontend/`);
- данные и действия — только через API по контракту (openapi-fetch + типы из `@calendar/api-contract`);
- интерфейс корректно работает с отдельно запущенным бэкендом: base URL настраивается env-переменной,
  на бэкенде будет включён CORS (см. STRUCTURE-PLAN, решение 8).

## Шаг 0. Артефакты контракта и каркас монорепо

Блокирует всё остальное.

1. `npm install` в корне; добавить `node_modules/` и `.DS_Store` в `.gitignore` (сейчас там только
   `.idea/`).
2. `npm run compile` в `api/` — проверить, что TypeSpec собирается (компилятор ни разу не
   запускался). Если вскроются ошибки в `.tsp` — сначала исправить их. Результат
   `api/openapi/openapi.yaml` закоммитить, как требует `tspconfig.yaml`.
3. `openapi-typescript` в devDependencies `api/`, скрипт генерации `api/types/schema.d.ts`, поле
   `exports` в `api/package.json` — фронт импортирует типы именованно из `@calendar/api-contract`.
4. Корневой каркас: workspaces `api` + `frontend`, `tsconfig.base.json`, корневые скрипты (`dev`,
   `build`, `test`, `contract`).
5. Обновить `docs/STRUCTURE-PLAN.md` (порядок: фронт до бэкенда) и `docs/TYPESPEC-PLAN.md`
   (отложенный шаг генерации выполняется здесь).

## Шаг 1. Каркас `frontend/`

- Vite + React + TS + React Router + **Mantine** (UI-библиотека из рекомендаций ТЗ), тесты на
  Vitest + testing-library (по STRUCTURE-PLAN).
- `src/api/client.ts` — openapi-fetch, типы из `@calendar/api-contract`; base URL из
  `VITE_API_URL` (по умолчанию в dev — Prism `http://localhost:4010`). Переход на реальный
  бэкенд — смена значения переменной, код клиента не трогаем.

## Шаг 2. Мок-сервер Prism

- `@stoplight/prism-cli` в devDependencies корня; скрипт `mock`:
  `prism mock api/openapi/openapi.yaml -p 4010`.
- Ответы Prism строит из примеров §8, уже прописанных в контракте (каталог `meeting-15`/`meeting-30`,
  фрагмент окна слотов, формат ошибок §8.8) — самописного мок-слоя и его сида на фронте нет.
- Сценарии ошибок (400 `validation_error`, 404, 409 `slot_taken`) в dev проверяются запросами с
  заголовком `Prefer: code=<код>` либо параметром `__code`; форму и обработку ошибок это покрывает.

## Шаг 3. Восемь экранов §7.1

- Header (§7.2), Home (§7.3), BookCatalog (§7.4).
- BookEventType (§7.5: три колонки, календарь со счётчиками «N св.»; форма §7.6 на той же странице
  через query-параметр `startAt`), Success (§7.7).
- Admin (§7.8), AdminEventTypes, AdminEventTypeNew (§7.9), AdminBookings (§7.10).
- Состояния экранов §7.11; форматы §7.12 через `Intl` + таймзона `Europe/Moscow`.
- Обработка ошибок: 400 — подсветка полей из `error.details`; 409 `slot_taken` — «Этот слот только
  что заняли…» и возврат к выбору слота с перезапросом; 404 — «Тип события не найден».

## Шаг 4. Тесты

F1–F5 (§11 «Интерфейс») на testing-library.

## Риски и допущения

- Шаг 0.2 может вскрыть ошибки компиляции TypeSpec — тогда сначала чиним `.tsp`.
- Prism stateless, а примеры слотов в контракте — со статическими датами (§8.5, «31 марта»): окно
  «14 дней от сегодня» в dev не совпадёт с текущей датой, а сценарий D8 (гонка → 409) на Prism не
  воспроизводится. Динамику проверяем в тестах F1–F5 (мок клиента с датами «от сегодня») и позже на
  живом бэкенде; Prism покрывает вёрстку, формы и обработку форматов ответов/ошибок.
- Бэкенд (миграции, Fastify + CORS, PostgreSQL в docker-compose) — следующим этапом после этого
  плана, по STRUCTURE-PLAN шаг 3.
